The decode path

Issue #1001 describes the problem precisely: docs.rs shows the modules but not the path — a clear documented path of what a user might actually need to start decoding. After PR #998, the public surface settles on api, image and error. This page is that path.

1. Start at jxl::api::JxlDecoder

JxlDecoder is the high-level API — it uses the typestate pattern to forbid invalid usage, so the compiler walks you through the decode: methods hand back a decoder in the next valid state (see the api::states module).

2. Read the image metadata

Once the header is parsed, JxlBasicInfo carries what you need to know before any pixel arrives: dimensions and bit depth, plus JxlAnimation timing for animations. Each frame is described by a JxlFrameHeader.

3. Request pixels your way

JxlDecoderOptions and JxlPixelFormat control how the buffers come out; decoded pixels land in a JxlOutputBuffer from the jxl::image module. Extra channels, when the bitstream has them, surface via JxlExtraChannel.

4. Handle errors with jxl::error

Fallible operations return Result values — the error module is the third public piece of the surface, and alongside api it is the only one a decoder integration should need.

What stays internal

bit_reader, color, entropy_coding, features, frame, headers, icc, render and util are implementation details; after #998 they are no longer part of the public API. If you find yourself reaching for them, JxlDecoderInner (the low-level, less-type-safe API in api) is the sanctioned escape hatch.

For item-level signatures, docs.rs remains the reference — this page is the path between the landing page and it.
